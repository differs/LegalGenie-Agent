# Chat-Canvas 法律办案台设计规格

## 状态

- 已确认
- 本规格覆盖并替代早期外壳草案 [2026-03-28-ai-command-center-design.md](/home/de/works/LegalMinds/docs/superpowers/specs/2026-03-28-ai-command-center-design.md)

## 目标

把当前偏“开发工作台”的前端外壳，重构成一个以对话为主线、以专业工作层为支撑、以计划面板为任务上下文的法律 AI 办案台。

目标不是做传统后台，也不是把现有多页壳简单美化，而是把主要使用路径改成：

1. 进入案件
2. 先看大输入框和推荐起手问题
3. 由 AI 给出计划
4. 围绕对话推进事实梳理
5. 需要时打开时间轴/证据/人物/导出 Canvas
6. 手动把对象带回对话继续深挖

## 非目标

- 不把产品改成单纯的聊天应用
- 不保留以左侧多页面导航为核心的信息架构
- 不让 AI 自动接管高风险写操作
- 不做竖排文本、竖向标题或任何违背常规横向阅读习惯的布局
- 不在这一轮改变后端权限、案件域模型和 API 契约

## 产品定位

产品定位是 `ChatGPT 主对话 + Deep Research 工作层`，但必须更接近法律专业工具，而不是通用 AI 聊天网站。

这个定位包含 5 个硬约束：

- 对话是主线，不是附属面板
- 专业视图通过 Canvas 工作层打开，不做传统页面跳转
- 右侧面板默认承担计划，再按需切换引用和结果
- AI 不抢方向盘，对象进入对话必须由用户显式授权
- 整个界面的第一优先级是可读性、层级和稳定感，而不是炫技式布局

## 设计原则

### 1. 对话优先

中央主区永远围绕对话消息流和输入区组织。用户不应该在“去时间轴页”还是“去证据页”之间做传统导航决策，而应该围绕当前问题推进。

### 2. 工作层而不是页面层

`时间轴 / 证据 / 人物 / 导出` 不是并列主导航页，而是从主对话中打开的专业 Canvas。它们服务于对话，不和对话争夺产品主线。

### 3. AI 先给计划，再给答案

进入案件后，右侧默认打开 `计划` 面板。用户在动手之前先看到 AI 认为的任务拆解、风险和建议路径。

### 4. 手动带入上下文

在 Canvas 中点选对象时，只允许高亮和浏览，不自动改写当前对话。用户必须显式点击 `带入对话`，该对象才进入输入区上方的上下文块。

### 5. 极轻左栏

左栏只承担案件切换、对话历史、用户菜单。专业能力入口不放到左栏，不做传统“应用菜单”。

### 6. 横向阅读优先

所有标题、标签、导航、状态都必须采用正常横向阅读方式。任何导致“竖排感”的排版都属于违例。

## 信息架构

桌面端采用四层结构：

1. 左侧轻栏
2. 中央主对话区
3. 右侧单面板
4. 中央 Canvas 工作层

### 整页结构

```text
┌ Left Rail ┬──────────── Main Conversation ────────────┬ Right Panel ┐
│ 案件切换   │ 案件上下文条 / 会话模式提示 / 状态         │ 计划        │
│ 当前案件会话│ 常驻快捷入口卡: 时间轴 证据 人物 导出      │ 引用        │
│ 全部对话   │ 推荐起手问题 / 对话消息流                  │ 结果        │
│ 新建会话   │ 可展开上下文块                             │ 收起/展开/固 │
│ 用户菜单   │ 大输入框                                   │             │
└───────────┴───────────────────────────────────────────┴─────────────┘
```

### 左侧轻栏

左侧轻栏只保留 5 类信息：

- 案件切换器
- 当前案件会话列表
- 全部对话入口
- 新建会话
- 用户菜单与设置

明确不放：

- 时间轴导航
- 证据导航
- 人物导航
- 导出导航
- 调试入口常驻露出

默认行为：

- 先显示“当前案件会话”
- 用户可以切到“全部对话”
- 全部对话中要明确标记所属案件

### 中央主对话区

中央主区是产品主角。默认进入某案件后，应首先看到：

1. 极简案件上下文条
2. 常驻快捷入口卡
3. 推荐起手问题
4. 大输入框
5. 对话消息流

#### 常驻快捷入口卡

快捷入口卡固定放在输入区上方，常驻可见，包括：

- 时间轴
- 证据
- 人物
- 导出

它们不是传统导航标签，而是“打开专业工作层”的入口。

#### 推荐起手问题

推荐问题用于替代传统 dashboard 卡片，帮助用户以自然语言进入案件工作，例如：

- 这个案件的关键争点是什么
- 时间线上有哪些证据缺口
- 帮我整理涉案人物关系
- 生成一版导出草案

#### 输入区与上下文块

输入区上方允许出现一个或多个 `可展开上下文块`。上下文块来自用户在 Canvas 中主动执行的 `带入对话`，默认简洁展示：

- 对象名称
- 对象类型
- 来源位置

展开后显示：

- 摘要
- 关键时间/编号
- 引用片段
- 清除上下文入口

### 右侧单面板

右侧面板默认打开 `计划`，并通过 Tab 切换到：

- 计划
- 引用
- 结果

右侧面板支持 3 个交互：

- 收起
- 展开
- 固定

约束如下：

- 默认只显示一个主面板，不做三栏常驻
- Canvas 打开时默认保留右侧面板
- 用户可以手动隐藏右侧进入专注模式

### 中央 Canvas 工作层

Canvas 是时间轴、证据、人物、导出的专业工作层。其行为是：

- 从中央快捷入口卡打开
- 覆盖中央主对话区
- 不影响右侧面板默认存在
- 底部输入框始终保留
- 关闭后回到原对话位置

Canvas 不是新页面，也不是浏览器级路由跳转。它是围绕当前会话打开的上下文工作层。

## 关键交互流

### 1. 进入案件

1. 用户进入已验证会话
2. 选择一个案件
3. 中央看到大输入框和推荐起手问题
4. 右侧默认出现 AI 计划
5. 左侧默认展示当前案件会话

预期结果：

- 产品第一感觉更接近对话工作台
- 但用户一眼就知道可进入时间轴、证据、人物、导出

### 2. 对话主线推进

1. 用户在中央输入问题
2. AI 返回回答
3. 如果任务复杂，右侧计划同步更新
4. 如果需要专业工作区，AI 在回答中引导用户使用快捷入口卡
5. 结论、引用和结果持续沉淀在当前会话

### 3. 打开 Canvas

1. 用户点击 `时间轴 / 证据 / 人物 / 导出`
2. 中央打开对应 Canvas
3. 右侧计划面板默认保留
4. 底部输入框仍然可用
5. 用户可选择收起右侧面板，进入更专注状态

### 4. 对象选中与带入对话

1. 用户在 Canvas 中选中节点、证据或人物
2. 系统只做高亮和详情展示
3. 不自动改写对话上下文
4. 用户点击 `带入对话`
5. 输入区上方出现可展开上下文块
6. 用户围绕该对象继续追问

### 5. 退出 Canvas

1. 用户关闭 Canvas
2. 返回原对话滚动位置
3. 已带入的上下文块保留，直到用户手动清除

## 状态流

### 1. 认证状态

- `SignedOut`
  只显示认证/连接页
- `Verifying`
  正在调用 `/auth/me`，不进入工作台
- `Ready`
  进入案件工作台

规则：

- 登录成功和注册成功都必须走 `/auth/me` 验证
- 只有 `Ready` 才允许进入工作台
- 不能再以“token 非空”作为进入工作台的依据

### 2. 主工作台状态

- `NoCase`
  已验证但未选择案件
- `ConversationEmpty`
  已选案件但还没有会话内容，推荐起手问题可见
- `ConversationActive`
  已有至少一轮有效会话，消息流成为主视觉

这里的主工作台状态是 `主状态`，只能在下列两项中二选一：

- `ConversationEmpty`
- `ConversationActive`

以下状态不是主状态，而是可并存的 `叠加状态`：

- `CanvasOpen`
  某个专业 Canvas 以覆盖层方式打开
- `RightPanelCollapsed`
  右侧面板被用户收起

也就是说，真实组合应当是：

- `ConversationEmpty + CanvasOpen`
- `ConversationEmpty + RightPanelCollapsed`
- `ConversationActive + CanvasOpen`
- `ConversationActive + CanvasOpen + RightPanelCollapsed`

以上只是合法组合示例，而不是穷尽列表。关键约束是：`CanvasOpen` 是覆盖层，不是替代对话的独立页面状态。

### 3. 右侧面板状态

- `Plan`
- `References`
- `Results`
- `Collapsed`
- `Pinned`

关系规则：

- 默认进入 `Plan`
- 用户显式操作后才切到 `References` 或 `Results`
- `Collapsed` 不丢失当前 Tab
- `Pinned` 是展示策略，不改变内容状态

### 4. Canvas 状态

- `Closed`
- `TimelineOpen`
- `EvidenceOpen`
- `PersonsOpen`
- `ExportsOpen`

规则：

- 同一时刻只允许一个 Canvas 打开
- Canvas 打开后，底部输入框仍然可用
- 关闭 Canvas 后返回原对话上下文
- Canvas 是覆盖层状态，不改变 `ConversationEmpty / ConversationActive` 主状态本身

### 5. 对象上下文状态

- `Unselected`
- `Selected`
- `InsertedCollapsed`
- `InsertedExpanded`
- `Cleared`

规则：

- `Selected` 只代表对象被点中
- 从 `Selected` 到 `InsertedCollapsed` 必须经过显式 `带入对话`
- 清除操作只移除当前输入区上下文，不影响 Canvas 选中态

### 6. 对话阶段切换规则

`ConversationEmpty` 与 `ConversationActive` 的切换必须明确，不允许由实现者自行猜测。

从 `ConversationEmpty` 进入 `ConversationActive` 的触发条件：

- 用户发送第一条问题
- 用户点击任一推荐起手问题并真正发起提问
- 用户在带有上下文块的情况下提交第一条追问

保持 `ConversationEmpty` 的情况：

- 只是选中了案件，但未发送任何问题
- 只是打开或关闭 Canvas，但未发起对话
- 只是选中对象，但未点击 `带入对话`
- 只是把对象带入输入区，但还未真正提交问题

从 `ConversationActive` 返回视觉空态的规则：

- 不做自动回退
- 只有用户显式新建会话，才回到新的 `ConversationEmpty`

这样可以保证推荐起手问题只在真正空会话时出现，不会在已有对话后反复闪回。

### 7. AI 执行状态

- `Auto`
- `ReviewRequired`
- `Guarded`

定义：

- `Auto`
  低风险、可逆、不改变案件结论的动作，可以直接执行
- `ReviewRequired`
  会改动案件内容，但可审阅、可追溯、通常可撤销的动作
- `Guarded`
  删除、合并、权限变更、跨案件写入等高风险动作，必须二次确认

## 视觉与排版约束

### 视觉方向

整体气质应是 `法律 AI 指挥台`，不是泛用聊天网站，也不是暖色后台。

视觉关键词：

- 冷静
- 可信
- 专业
- 审计可追溯

### 色彩方向

建议采用：

- 深蓝灰作为主色
- 铜金/琥珀作为强调色
- 暖白或浅米色作为背景底

避免：

- 大面积发黄底色覆盖整个界面
- 高频高饱和点缀色
- 品牌色和风险色混用

### 排版约束

- 所有主要文案保持正常横向阅读
- 不使用竖排标题、旋转标签或会造成阅读中断的纵向布局
- 主标题、正文、辅助说明、状态标签必须拉开层级
- 同屏只保留有限数量的一等按钮

## 当前代码库中的实现边界

现有实现已经具备以下基础：

- `/auth/me` 验证闸门
- 右上操作者状态
- `shell.rs` 中的外壳状态模型
- 各业务页已有最小可用实现

当前实现的主要问题是：

- [main.rs](/home/de/works/LegalMinds/frontend/src/main.rs) 仍承担过多外壳职责
- [shell.rs](/home/de/works/LegalMinds/frontend/src/shell.rs) 还停留在“Brief 导航壳”阶段
- 各业务视图仍按“页面”组织，而不是 Canvas 工作层
- 快捷入口、对话主轴、右侧计划面板、对象上下文块尚未正式形成一套联动结构

因此实现时应优先：

1. 先拆外壳
2. 再做主对话布局
3. 再挂 Canvas 工作层
4. 最后把旧页面入口降为内部视图实现

## 现有 Tab 到新工作层的迁移映射

当前前端仍以 [shell.rs](/home/de/works/LegalMinds/frontend/src/shell.rs) 的 `Tab` 驱动主外壳，包含：

- `Brief`
- `Cases`
- `Timeline`
- `Files`
- `Persons`
- `Search`
- `Exports`
- `Logs`

新设计不是直接删掉这些能力，而是重新定义它们在外壳中的角色。

迁移映射如下：

- `Brief`
  保留为默认主会话工作台入口
- `Cases`
  保留为案件选择与切换入口，但不再占据主工作导航权重
- `Timeline`
  从主导航页降级为 `时间轴 Canvas`
- `Files`
  从主导航页降级为 `证据 Canvas`
- `Persons`
  从主导航页降级为 `人物 Canvas`
- `Exports`
  从主导航页降级为 `导出 Canvas`
- `Search`
  不作为左栏一级入口；优先以主对话能力和右侧引用/结果联动承载，必要时保留为次级工具入口
- `Logs`
  不作为左栏一级入口；保留为审计相关的次级入口，可放入用户菜单或案件工具区

实现含义：

- 旧的 `Tab::Timeline / Files / Persons / Exports` 不再直接驱动左栏主导航切页
- 它们应演进为 `CanvasKind` 或等价的覆盖层状态
- 旧页面组件本身可以先复用，作为 Canvas 内部内容承载
- 左栏保留的是案件与会话，不再保留这些专业视图的一级入口

这条迁移规则是为了在不推翻现有页面内容的前提下，把“多页工作台”平滑收束为“对话主线 + 工作层”。

## 验收标准

当以下条件全部成立时，才算设计落地正确：

- 已验证会话进入后，默认看到的是主对话而不是传统多页工作台
- 左侧只承担案件和会话，不再是专业功能总导航
- `时间轴 / 证据 / 人物 / 导出` 通过常驻快捷入口卡打开
- 打开专业视图时采用 Canvas 工作层，而不是切页面
- 右侧默认显示计划，引用和结果按需切换
- Canvas 中可继续提问 AI
- 选中对象不会自动污染对话上下文
- 只有用户主动 `带入对话`，上下文块才进入输入区
- 所有主要文本和操作都保持正常横向阅读

## 实现建议

这一轮实现不应直接在 [main.rs](/home/de/works/LegalMinds/frontend/src/main.rs) 继续堆壳，而应按职责拆出：

- 工作台骨架组件
- 左侧会话栏组件
- 主对话组件
- 右侧面板组件
- Canvas 容器组件
- 上下文块组件
- 针对现有页面的 Canvas 适配层

这样才能避免新的交互继续长进单个巨石文件。
